Bludia has a small set of building blocks. Once you know them, the rest of the docs read quickly.

## The building blocks at a glance

| Concept | One-line definition | Analogy |
| :-- | :-- | :-- |
| **Project** | One isolated backend: data, users, keys, hooks, settings | A database + API server |
| **Collection** | A type of data with a set of fields, addressed by its slug | A table |
| **Field** | A typed attribute on a collection, with validation rules | A column |
| **Record** | One item stored in a collection | A row |
| **Relation** | A link between two collections (1:1, 1:N, N:N) | A foreign key or join table |
| **API key** | Credential that identifies your app to the API (`X-BLUDIA-API-KEY`) | An app secret |
| **Authentication guard** | Turns a collection (for example `users`) into a login system | An auth provider |
| **End user** | A person who signs in to *your* app through a guard | Your customer |
| **Team member** | A person who manages the project in the Bludia dashboard | Your colleague |
| **Role** | A named group of end users with per-collection permissions | A user group |
| **Row policy** | A rule that limits which records a role can see and change | Row-level security |
| **Hook** | Go code that runs before or after a record is written | A database trigger |
| **Channel / template** | Email delivery settings and reusable message content | Mail config + email template |

## How the pieces fit together

```text
Project
├── Collections ── Fields ── Records
│        └── Relations between collections
├── API keys            → who may call the API (platform or end_users)
├── Authentication guards
│        └── Roles → Collection permissions + Row policies
├── Hooks               → before/after insert, update, delete
├── Messaging           → channels + templates
├── Files, reports, dashboards, PDF templates
└── Functions (buttons, record events, schedules)
```

<AccordionGroup>
  <Accordion title="Projects" icon="folder-kanban">
    A **project** is the boundary around one application. Collections, records, keys, guards, hooks, and settings never leak between projects. Team members are invited per project. See [Projects](/projects).
  </Accordion>

  <Accordion title="Collections, fields, and records" icon="database">
    A **collection** defines a type of data, like `customers` or `bookings`. Each collection has a **slug** used in API URLs: `/collections/customers/records`.

    **Fields** define the shape of each record: type (text, number, date, select, relation, file…), whether it's required or unique, and [validation rules](/database/validation).

    **Records** are the stored items. Every record has system fields: `id`, `slug`, `created_at`, `updated_at`, `published_at`. In API responses, field values appear as top-level keys named after the field.
  </Accordion>

  <Accordion title="Relations" icon="link">
    **Relations** connect collections: `one_to_one`, `one_to_many`, or `many_to_many`. You can expand related records in API responses with the `with` query parameter. See [Relations](/database/relations).
  </Accordion>

  <Accordion title="API keys: platform vs end_users" icon="key">
    Every API request carries an **API key** in the `X-BLUDIA-API-KEY` header. A key has an **auth type**:

    - **`platform`**: acts with full project access. Use only on trusted servers.
    - **`end_users`**: requires a signed-in end user's `Authorization: Bearer <access_token>` on data routes. Role permissions and row policies apply. Use in browser and mobile apps.

    See [API authentication](/api/authentication).
  </Accordion>

  <Accordion title="Authentication guards and end users" icon="key-round">
    An **authentication guard** connects login to one of your collections. You pick the collection (for example `users`) and the login field (for example `email`); Bludia adds a password field. End users then register and log in at `/auth/{guard}/register` and `/auth/{guard}/login` and receive a short-lived JWT access token plus a refresh token.

    End users are records in your own collection, so you can add any profile fields you like. See [Authentication](/authentication/overview).
  </Accordion>

  <Accordion title="Authentication vs authorization" icon="shield-check">
    - **Authentication** answers *who is this?* (guards, login, tokens).
    - **Authorization** answers *what may they do?* (roles, collection permissions, row policies).

    Bludia checks both on every end-user request: first the collection permission for the action (`read`, `create`, `update`, `delete`), then the row policies that filter which records are visible. See [Authorization](/authorization/overview).
  </Accordion>

  <Accordion title="Roles, permissions, and row policies" icon="users">
    A **role** belongs to a guard. Each guard starts with a default role, `user`, which new registrations get automatically.

    **Collection permissions** grant a role actions on a collection: `can_read`, `can_create`, `can_update`, `can_delete`, plus `can_export`, `can_import`, `can_execute_actions`, `can_manage_schema`.

    **Row policies** narrow access to specific records, for example *only records I created* (`owner`), *records where `status` = `published`* (`field_equals`), or *records linked to me through a relation* (`relation`). With no allow policy, end users see only records they created. See [Row-level security](/authorization/row-level-security).
  </Accordion>

  <Accordion title="Hooks" icon="webhook">
    A **hook** is Go code attached to one collection and one event: `beforeInsert`, `afterInsert`, `beforeUpdate`, `afterUpdate`, `beforeDelete`, or `afterDelete`. Bludia compiles it to WebAssembly and runs it in a sandbox.

    - **Before** hooks run synchronously: they can change the record or reject the operation.
    - **After** hooks run asynchronously after the write is committed: use them for notifications and side effects.

    See [Hooks](/hooks/overview).
  </Accordion>

  <Accordion title="Messaging" icon="mail">
    A **channel** stores delivery settings (for example an SMTP email account). A **template** stores reusable content with `{{variables}}`. Hooks and authentication flows (like email verification) send messages through them. See [Messaging](/messaging/overview).
  </Accordion>

  <Accordion title="Reports, dashboards, and scheduled functions" icon="chart-column">
    **Reports** query and aggregate records. **Dashboards** show widgets (stats, record lists). **PDF templates** render records into documents. **Scheduled functions** run business logic once, on an interval, or on a cron schedule, optionally once for each matching record.
  </Accordion>
</AccordionGroup>

## The request lifecycle

What happens when your app calls `POST /collections/bookings`:

```text
1. API key check        X-BLUDIA-API-KEY valid, not revoked or expired     → else 401/403
2. CORS check           Origin is in the key's allowed origins             → else 403
3. Rate limit           Requests per minute for this key                   → else 429
4. End-user check       (end_users keys) valid Bearer access token         → else 401
5. Permission check     (end_users keys) a role has can_create on bookings → else 403
6. Validation           Body matches field types and rules                 → else 422
7. beforeInsert hook    May modify the record or abort                     → abort = nothing saved
8. Write                Record saved; owner = signed-in end user
9. afterInsert hook     Runs asynchronously after commit
10. Response            201 Created with the record
```

## The development model

<Steps>
  <Step title="Model">Collections, fields, relations.</Step>
  <Step title="Expose">API keys and the REST API.</Step>
  <Step title="Secure">Guards, roles, collection permissions, row policies.</Step>
  <Step title="Extend">Hooks, messaging, scheduled functions.</Step>
