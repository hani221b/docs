Bludia's database is where your application data lives. You design the schema in the dashboard; Bludia stores records in PostgreSQL, validates every write, and exposes each collection through the REST API.

```text
Project
└── Collection: bookings              (slug used in the API: /collections/bookings)
    ├── Fields: customer (relation), service (relation), date (datetime), status (select)
    └── Records:
        ├── #101  { customer: 25, date: "2026-12-01T10:00", status: "confirmed" }
        └── #102  { customer: 31, date: "2026-12-02T14:30", status: "pending" }
```

## Key behaviors

| Behavior | Detail |
| :-- | :-- |
| Validation on every write | Dashboard, API, imports, and hooks go through the same field rules. |
| Partial updates | On update, omitted fields keep their value; `null` or `""` clears a field. |
| Soft delete | Deleted records go to the trash and can be restored or permanently deleted. |
| Record history | Every record keeps a change history you can view in the dashboard. |
| Optimistic concurrency | Send the record `version` (or `If-Match`) on update to avoid overwriting someone else's change; a stale version returns `409`. |
| Ownership | Records created by a signed-in end user are owned by that user; row policies use this. |
| Passwords never returned | Values of `password` fields are hashed and never included in responses. |
