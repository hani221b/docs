Bludia validates every create and update against your field definitions, whether the write comes from the dashboard, the API, an import, or a hook. Invalid writes are rejected with **`422 Unprocessable Entity`** and nothing is saved.

Configure rules in the dashboard on each field under **Validations**.

## Core rules

| Rule | Applies to | Effect |
| :-- | :-- | :-- |
| `required` | all | Value must be present and non-empty on create |
| `unique` | all except relation | No other record has the same value |
| `nullable` / `allow_null` | all | Allows an explicit `null` |
| `strict_type` | all | Disables type coercion; `"42"` is rejected for a number |
| `readonly` / `computed` | all | Value can't be set by clients |

## Cross-field rules

| Rule | Example | Meaning |
| :-- | :-- | :-- |
| `same_as` | `password_confirm` same as `password` | Values must match |
| `different_from` | `backup_email` different from `email` | Values must differ |
| `greater_than` | `end_date` greater than `start_date` | Compare to another field |
| `less_than` | `discount` less than `price` | Compare to another field |
| `xor_with` | `phone` xor `email` | Exactly one of the two may be set |
| `unique_scope` | `seat` unique per `event` | Unique among records sharing other field values |
| `composite_unique` | `trip_code` unique together with `year` | The combination of this field and the listed fields must be unique |

### Unique together

A trip code may repeat from one year to the next, but only once per year. Put the rule on the trip code field and list the other fields by id:

```json
{ "id": 1, "name": "trip_code", "type": "text", "validations": { "composite_unique": ["2"] } }
```

In the collection editor, open **Unique Together** on the field and pick the other fields. The database enforces the rule, so it also holds when two people save at the same moment. A record with an empty value in any of these fields is not checked. Adding the rule while duplicates exist is refused with a 422 error. A field that a rule uses can't be removed until the rule is removed.

## Conditional rules

Apply rules only in some situations. A condition compares another field to a value:

```json
{ "field": "type", "operator": "=", "value": "company" }
```

| Rule | Meaning |
| :-- | :-- |
| `required_if` | Required when the condition is true (for example `company_name` when `type = company`) |
| `prohibited_if` | Must be empty when the condition is true |
| `validate_if` | Run this field's other rules only when the condition is true |

## Error response

```json
{
  "status": false,
  "message": "Field 'email' must be a valid email address.",
  "errors": [],
  "request_id": "9b2f6c1e-4a7d-4e0b-9a51-2f1d3c8e7a10"
}
```

Error messages name the field (its label, or its name when it has no label) and the failed rule, for example:

- `Field 'title' is required.`
- `Field 'email' must be unique.`
- `Field 'code' does not match the required pattern.`
- `Field 'amount' has an invalid value for type 'number'.`

### Custom messages

You can replace the message of any rule on a field. In the field's settings, open **Custom error messages** under a rule section, or fill in the message under **Required** or **Unique**. In the schema they live in `validations.messages`, keyed by rule:

```json
"validations": {
  "min_length": 3,
  "messages": {
    "required": "Please enter a code.",
    "min_length": "{field} needs at least 3 characters (you entered {value})."
  }
}
```

`{field}` is replaced by the field's label and `{value}` by the submitted value. Rules without a custom message keep the default.

See [Errors](/api/errors) for the full error format.
